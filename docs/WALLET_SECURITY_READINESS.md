# Wallet release security review

The HTTP legacy deposit route was already disabled; its unused service implementation now also fails closed. Purchase fulfillment records pre-credit balance as post-credit minus credited coins, binds the status claim to the observed amount, quantity and payment mode/method, and checks frozen state at the wallet mutation. Unknown completion modes and invalid quantities are rejected; live completion requires a live order, explicit canonical EVM transaction hash and server-side verification metadata. Metadata is not proof of payment by itself: only the independently verified provider flow may invoke fulfillment. Unique providerOrderId and transactional claim remain duplicate guards. No payment endpoints enabled, no funds moved, no provider or wallet address changed, no historical ledger rewritten.

CI now explicitly includes purchase and no-bonus regression suites. Remaining gates: real PostgreSQL race/rollback tests on isolated synthetic accounts, independently verified provider payment ownership and replay across orders, consistent reconciliation snapshots before any automated freeze, review of PIN/2FA races, audit and real staging acceptance. Existing historical ledger before-balance errors must be assessed separately, never silently rewritten. No production financial certification.


## Reconciliation snapshot hardening
Reconciliation now reads the wallet and ledger and writes both currency reports and discrepancy audits in one PostgreSQL repeatable-read transaction with bounded wait/runtime. Signed REFUND movements retain their actual direction, including negative purchase refunds. Missing wallets are not created by reconciliation. Automated reconciliation freezing fails closed until ledger completeness and a current-state fencing protocol are independently verified. Reports are snapshot evidence, not a current freeze decision. No historical ledger is rewritten. Actual PostgreSQL concurrency and rollback acceptance remains required for this change.

## Provider webhook authentication and chain watcher safety
Coin and verification payment webhook services now verify standard HMAC-SHA256 of the exact raw body using a constant-time byte comparison; legacy concatenated SHA256 is rejected. Chain watcher amount/time matches are reconciliation-only, even if a single order matches; the watcher no longer fabricates authenticated provider events or fulfills coin/badge purchases. This deliberately removes heuristic auto-crediting. The existing public coin webhook remains under maintenance. Independently verified provider order ownership, provider signer compatibility, cross-order/cross-product replay protection and safe resolution of pending payments remain release gates. No provider configuration or production deployment changed.

Webhook field binding: both coin and badge service entrypoints now reject unsigned changes to event ID, order, hash, network, asset, amount, status and supplied optional fields, before event persistence or fulfillment. Optional recipient/confirmation fields are then taken from the signed body, not caller omissions. This does not prove that the provider independently verified order ownership or prevent one on-chain transaction being accepted by separate product tables; those remain gated. Regression tests sign the exact supplied event and reject tampered fields.

## Cross-product transaction replay fence
A new additive migration creates a permanent BlockchainPaymentClaim registry, backfills canonical historical coin/badge references (including refunded orders), and installs transactional triggers on both purchase tables. Hashes are canonicalized globally across networks conservatively: the same hash cannot fund multiple orders or products. Historical duplicate ownership causes migration rollback, not a chosen winner. The claim rolls back with failed fulfillment and survives refunds/deletion. Badge live activation now requires a live order, canonical reference and on-chain metadata, and binds amount/plan/network/mode/expiry at the mutation. Coin refunds reject PAID orders that may not have been credited. This is not independent provider order ownership proof; no real payments, production deployment or migration applied. Real concurrent database validation and historical conflict preflight required.


## Transfer OTP challenge fencing
Transfer and standalone OTP paths require the original session when present. Success and failed-attempt writes conditionally match the observed hash, attempt count, maximum, session, unconsumed state and unexpired challenge; stale updates fail closed. High-value transfer authenticator verification remains required once observed and is tied to the verified OTP hash. This does not yet lock PIN/2FA credential state throughout the financial transaction, or coordinate real external withdrawals and cancellation. CI and real database race verification remain required for this change.

## Financial authorization row fencing
Transfers and withdrawal reservations now hold the verified PIN row (exact hash, clean failed-attempt counter and no lock) until the balance transaction commits. High-value transfers and withdrawals additionally lock the observed authenticator enabled/secret state, and strict wallet 2FA verification must match that secret before consuming a code. Changed state rejects before financial mutation; challenge consumption and financial writes remain in the same transaction. Existing low-value transfer 2FA policy is unchanged. No schema or provider change. CI and real PostgreSQL lock-order/race acceptance required. This does not certify external payout coordination, backup-code rotation policy, or all account recovery paths.

## Withdrawal payout reservation fence
The admin-only reserve-payout endpoint uses the existing PROCESS_WITHDRAWALS permission and requires explicit operator confirmation of prior unsent reconciliation. PENDING -> PAYOUT_RESERVED is a single-winner transaction with exact intent and pending ledger validation plus audit. No money is sent. Completion requires this distinct state; PENDING-only cancellation/rejection cannot refund reserved payouts, and new requests are blocked while any withdrawal is pending, reserved or legacy processing/approved. A lost or uncertain reservation stays fenced, with no automatic expiry/refund. Legacy PROCESSING is not silently interpreted as the new reservation. External operator attestation is not independent proof; reconcile legacy pending/processing history before rollout, and design a reviewed recovery/unsent-proof path before enabling any automated payout. CI and real database acceptance required; no provider enablement.

## Withdrawal settlement replay and historical evidence
An additive migration extends BlockchainPaymentClaim to withdrawal references, reserving historical valid hashes in canonical form without rewriting source records. Duplicate owners (including coin/badge), invalid non-null legacy references and completed USDT withdrawals missing a hash stop migration for manual reconciliation. New references are canonical and immutable once recorded, with permanent claims retained after row deletion. Ordinary refunds require no transaction reference and bind exact withdrawal and ledger values. The migration cannot establish historical payments from missing records or prove an external payout belonged to a specific request. Run read-only historical review before applying to any existing database; reconcile ambiguous reservations manually. CI tests use disposable PostgreSQL only.
