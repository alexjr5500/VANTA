# Distributed maintenance readiness

VANTA_DISTRIBUTED_MAINTENANCE_ENABLED=true requires VANTA_MAINTENANCE_DIRECT_DATABASE_URL, a direct/session-affine connection to the exact same writable PostgreSQL database used by all participating app replicas. Verify provider topology, role, and database identity first; the helper only checks writable-primary status and rejects an explicit pgbouncer=true parameter, not every possible proxy. All replicas must use the same coordination mode. No production variables changed.

Stable two-integer PostgreSQL advisory locks protect overlapping live stale-session, OAuth expiry, follower reward expiry, birthday/anniversary and badge expiry sweeps. A losing contender skips work; an unavailable coordination connection never runs work unlocked. The dedicated session closes in finally, including on work errors; lock release is automatic if the connection dies. Periodic live sweeps are now tracked by the HTTP background drain. Independent tasks can still run concurrently; budget up to five additional direct connections per process (actual simultaneous task types depend on timing).

This is mutual exclusion while the lock session is alive, not exactly-once scheduling: another replica can execute the same task sequentially, and session loss or failover during an in-flight task can permit overlap. Existing service-level transactional/idempotency guarantees remain essential, especially for wallet-related work. A skipped or failed task is retried by its existing schedule (OAuth startup-only sweep has no periodic retry). Existing task handlers may catch their own errors; successful lock ownership is not proof of task success. Legacy timers, startup seeding and cache warming are not covered. Verify idempotency, bounded task sizes, cross-server lock contention, kill/restart and DB failover in isolated staging before activation. CI covers independent real PostgreSQL connections, contention, release after error and unavailable database. No new tables or migrations.
