# Database sharding and partition readiness

Prefer measured optimization and a managed read replica before sharding. PostgreSQL time partitioning on one database is not horizontal sharding. Current Prisma schema uses global uniqueness and cross-domain relations. Identity/session, wallet/ledger, transfers, payments, moderation and permission-critical data stay on the primary until an independently reviewed consistency model exists.

A read-only catalog assessment covers a fixed set of candidate tables (analytics, interactions, views, notifications, messages, posts, videos, follows, users and wallets). Run only against an explicitly verified isolated staging database: VANTA_STAGING_SHARDING_ASSESSMENT=yes VANTA_STAGING_SHARDING_DATABASE_URL=<isolated-url> npm --prefix backend run db:assess-sharding. Optional schema defaults to public. The CLI rejects the exact application DATABASE_URL, but URL inequality alone does not establish isolation. Never use production endpoints. The query reads catalogs only, reports approximate reltuples/size, inbound/outbound FK counts, existence of candidate column and unique indexes missing the candidate key (INCLUDE columns do not count). Partitioned parent size/estimate excludes children; review separately. Missing relations or keys and unknown estimates are explicit. Nothing routes, copies, partitions or migrates records; every result has migrationApproved=false.

Candidate strategy: evaluate time partitioning for append-heavy analytics before cross-database movement; consider notification recipient, conversation, content owner and social graph domains only after profiling. Do not assume user IDs distribute uniformly, or that all queries are single-shard. Measure QPS, IOPS, size, growth, hot keys, cross-domain joins, unique constraints, foreign-key dependencies and transaction semantics. Design versioned shard mapping, routing, rebalancing, global IDs, authorization, cross-shard query fan-out, reconciliation, deletion/export and rollback before any migration. Finance remains single-authority; no dual-write or eventual ledger correctness. Tests create synthetic catalog fixtures in a disposable CI database. No new production resource or schema mutation.
