# Application server traffic readiness and drain

The existing /health diagnostic and deployment configuration are unchanged. New endpoints: GET /health/live returns 200 when the HTTP process is responding, and GET /health/ready returns 200 only after successful startup and a successful bounded database reachability probe. During startup, DB failure, required Redis failure or drain it returns 503. Responses are no-store and expose only a generic state/reason. Database probes have a 1.5s response deadline, one outstanding query per process and a 1s cached result; a timeout does not cancel the underlying query. VANTA_READINESS_REQUIRE_REDIS=true also requires the opt-in Redis adapter to report ready. Redis status is a connection signal, not an end-to-end dependency check.

VANTA_GRACEFUL_SHUTDOWN_ENABLED=true is isolated staging opt-in. SIGTERM/SIGINT irreversibly marks the server draining, rejects new HTTP work and new Socket.IO handshakes, stops cache warming and the three tracked startup sweeps, closes Socket.IO and HTTP, then disconnects Redis and Prisma. A 25-second overall deadline exits nonzero on timeout or cleanup failure. Accepted HTTP requests may finish until the deadline; in-flight socket event handlers, legacy job queues, other module timers and interrupted uploads are not guaranteed drained. Existing sockets disconnect and clients must reconnect/retry safely. No load balancer or production platform configuration is changed.

In a dedicated staging HTTP service, verify the platform termination allowance exceeds 25s before opting in. Test liveness/readiness, a controlled DB outage and recovery, optional Redis outage, SIGTERM during a long request/upload, socket reconnect and duplicate transaction prevention. Confirm the load balancer actually removes unhealthy instances and does not route new connections after a drain. Review startup sweeps and global socket/presence/queue ownership before enabling multiple replicas. Keep production flags and healthcheck path unchanged until acceptance and approval.
