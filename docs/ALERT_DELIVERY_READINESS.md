# Central alert delivery readiness

Opt-in VANTA_ALERT_WEBHOOK_ENABLED=true requires an operator-approved HTTPS VANTA_ALERT_WEBHOOK_URL, exact VANTA_ALERT_WEBHOOK_ALLOWED_ORIGIN, secret VANTA_ALERT_WEBHOOK_TOKEN (24+ printable non-space characters), VANTA_ALERT_ENVIRONMENT and VANTA_ALERT_SERVICE. Set these securely on isolated staging only after selecting a trusted receiver. No default destination. Do not expose tokens. Receiver should authenticate bearer token, enforce payload schema, deduplicate eventId and correlate environment/service/code/instanceId; provision trusted TLS and egress controls independently. The origin check is an operator guardrail, not network-level SSRF protection against a malicious configured destination.

HTTP, dependency and queue alerts use an explicit allowlisted event schema without raw logs, request data, query strings or user data. HTTP alerts use existing sustained-window gate; dependency alerts include recovery; queue CLI emits per-run degraded signals and requires receiver-side incident deduplication. Delivery is sequential and best-effort, at most 24 waiting events plus one in flight, 3s request deadlines, no redirects, up to three attempts with short backoff for network errors, 429 and 5xx. Other 4xx are terminal. Stable eventId/idempotency-key across retries; no persistent queue and no exactly-once guarantee. Shutdown attempts flushing within existing global drain deadline; process death, full queue or receiver outage can lose events. Logs remain fallback. This does not replace centralized metric aggregation or external dead-process monitoring.

CI exercises mocked destinations only. Before enabling, verify an isolated receiver, receipt and deduplication of a synthetic incident, recovery, invalid token, timeout, failure handling, on-call ownership, incident routing and operational cost. No provider has been configured or contacted and production variables are unchanged.
