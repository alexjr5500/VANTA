# Database scaling readiness (6.9 / 6.10)

Existing application reads, writes, transactions, migrations and queue claims continue using the primary Prisma client. No automatic replica routing, sharding, failover or database provisioning is enabled.

Optional per-process settings: VANTA_DB_CONNECTION_LIMIT (1–100) and VANTA_DB_POOL_TIMEOUT_SECONDS (1–60). Unset preserves the original URL; explicitly configured values replace matching Prisma URL parameters. A bounded pool must be sized against all application replicas, workers, migrations, admin connections and reserved server capacity. The connection-budget helper calculates this combined estimate; it does not query or enforce a provider quota. Example: 3 HTTP x 8 + 2 workers x 4 + 10 reserved = 42 connections. Measure the real database limit, connection utilization and pool wait times before choosing settings.

For a **verified isolated staging primary and physical streaming standby of the same cluster**, use separate read-only probe credentials and verify the endpoint identity in the provider dashboard first. Set VANTA_STAGING_DB_PROBE=yes, VANTA_STAGING_PRIMARY_PROBE_URL and VANTA_STAGING_REPLICA_PROBE_URL securely; run `npm --prefix backend run db:verify-replica` after build. The URLs must differ from each other and the application DATABASE_URL. This is a guardrail, not proof of environment identity. The probe requires visibility of the WAL receiver (for example, an approved monitoring role). It verifies the primary is not in recovery, the standby is in recovery and read-only, its receiver is streaming and its replay is within 16 MiB WAL distance of the primary at sampling time. This initial byte threshold is not a time-lag SLA. It does not prove both endpoints are from the same cluster or that recent writes are visible. An unavailable/blocked probe exits 2 and emits only aggregate diagnostics.

CI tests pool configuration, budget calculations, blocked replica states and rejection of a real writable PostgreSQL instance presented as a replica. A successful physical standby acceptance test is still required. Before routing any reads, select and review an explicitly eventual-consistency-safe query allowlist; keep wallet, authorization, moderation, privacy, sessions, queue claims and read-after-write flows on primary. Measure lag and failover and prove application rollback. Sharding requires workload and partition-key evidence and remains separate.
