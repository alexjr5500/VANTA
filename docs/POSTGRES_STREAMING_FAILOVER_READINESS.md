# PostgreSQL replication and failover readiness

The read-only replica probe now blocks when physical cluster identity (pg_control_system system_identifier) or database name differs or cannot be read. It also rejects an allegedly primary endpoint that is read-only. A dedicated staging probe role may need explicit EXECUTE permission on pg_control_system(); do not grant superuser merely to satisfy a probe. Matching cluster identity alone is not proof that the standby follows the current primary timeline; verify sender/receiver topology, fencing and timeline with the provider. The application still uses the primary exclusively.

A new GitHub-hosted CI job creates an isolated Docker network and PostgreSQL 16 primary plus physical pg_basebackup streaming standby, using synthetic data, temporary local ports and test credentials. It checks replay of a marker and a positive replica readiness result, rejects a primary masquerading as replica, then stops the primary before promoting the standby, verifies replayed marker and ability to write. Resources are removed on exit. This is a disposable exercise, not a production failover or guarantee of zero data loss. GitHub CI run 45591390607 passed the disposable streaming replica and fenced failover exercise on commit e1c7b06 (2026-11-25). Vercel preview and the regular staging worker also succeeded. This does not verify managed Railway replication.

Before managed staging adoption: provision an isolated supported topology with cost approval; verify roles/identity/streaming, lag under controlled load, RPO and RTO, provider fencing, DNS/connection reconnection, backups, recovery and rollback; test intentional replica lag and outage. Keep wallet, authentication, authorization, moderation and other consistency-critical reads on the primary. No automated application promotion or automatic write failover; no production changes.
