## Initial staging HTTP smoke benchmark

After verifying the exact isolated Railway staging service and its dependencies, set VANTA_STAGING_LOAD_TEST=yes, VANTA_LOAD_TEST_ORIGIN and VANTA_LOAD_TEST_ALLOWED_ORIGIN to its exact HTTPS Railway staging origin. These variables are guardrails, not a proof of environment identity. Run `npm --prefix backend run load:staging`. Default endpoint /health/ready, 100 measured requests, concurrency 2, 3-second timeout, p95 budget 300 ms. Optional path /health/live or /api/version; requests capped at 300, concurrency at 10, no redirects, no credentials and no writes. A preflight must pass; stop issuing requests after three failures (in-flight requests may finish). One 100 ms delay per worker limits request issue rate. Report successful-response p50/p95/p99, errors, status counts, elapsed time and achieved requests/sec. CI tests the harness with simulated responses only. This does not measure feed/chat/reels, identify replica distribution or prove capacity. No live benchmark until staging is healthy and explicitly verified. Do not run against production.

Replica sampling: on a separately verified Railway environment named exactly staging, VANTA_STAGING_INSTANCE_PROBE=yes enables an opaque per-process random UUID header only on /health/ready. Set VANTA_LOAD_TEST_MIN_INSTANCES=2 (or required count up to 10) with the readiness benchmark to require valid markers on every successful measured response and at least that many distinct process markers. Only aggregate counts are reported. A restart can introduce a new identifier; observations do not prove simultaneous replicas, fair balancing or stickiness. Verify actual topology and stable deployments independently; disable header afterward. No live load tests or scaling changes performed.

## Home/feed read path optimization

Seven independent discovery reads now run in three bounded stages (maximum three simultaneous reads per request), after the existing follow lookup. Ranking, bucket limits and fresh repost/gift enrichment are retained. The followed-post read now excludes moderation-removed posts. Personalized cache keys include a digest of cursor, page size and seed under the existing invalidation prefix. Global trending/explore cache only their canonical default first page to preserve existing exact-key invalidation. Nondefault requests bypass that cache. Basic and trending post cursor pages now return the last delivered row rather than discarded lookahead, with stable ID tie-breaking. Tests cover key separation, lookahead and concurrency/failure behavior. No measured latency improvement claimed: compare p95, DB pool pressure and correctness on isolated staging; three-way fanout may increase concurrent pool utilization. Existing TTL and invalidation limitations remain; no migration or production config change.

## Chat and notification query optimization

Conversation list enrichment previously issued an unread count per conversation and individual presence follow and read-receipt preference queries. It now uses one groupBy over visible page IDs with the same moderation/deletion/recipient predicates, one conditional follow lookup, and one batched receipt sanitization call (which may separately check follower-only receipts). Empty pages skip enrichment. Existing membership and privacy logic retained. Stable ID tie-breakers for conversation and latest-message ordering. Notifications page and unread count run concurrently; last-delivered cursor avoids skipping lookahead. Existing Message conversationId/deletedAt/createdAt, MessageRead and Follow indexes are the initial baseline; do not add unmeasured overlapping indexes. Review EXPLAIN (ANALYZE, BUFFERS) on isolated representative staging data before selecting new indexes. Grouped count can still be expensive on large unread histories; benchmark pool pressure, rows examined and p95. No actual latency claim.

## Frontend startup and mobile bandwidth

Home no longer fetches two unused trending/suggested discovery lists. Live discovery is refreshed immediately when visible/online, every 15 seconds while available, and on visibility/network recovery, without overlapping polls; late results are ignored after cleanup or while unavailable. The eager StoryComposer shell retains its open-command registration and defers the text, status and media editors via dynamic imports. Native picker remains a deliberate in-editor action; first editor open can incur a chunk download. Test actual Android WebView cold/warm opening, camera/gallery gestures, slow network and upload continuity before release. No measured startup or byte reduction claimed; compare route JS transfer, main-thread time and network waterfall on a representative device. Existing background upload indicator and socket subscriptions are unchanged.

## Android shell and mobile layout

Ordinary WebView resource requests now bypass native gallery initialization and permission checks. Requests under the reserved gallery path still follow every existing trust, nonce and permission gate, including invalid paths. Native thumbnail decoding retains its existing resolution and no-store policy; bitmap memory is released even when JPEG encoding fails. Revoked gallery access clears enumerated entries when listing is requested. Identical native system-bar padding is no longer reapplied. Late FCM token dispatch is guarded against destroyed/replaced WebViews, and the WebView is detached before destruction. Web viewport resize/scroll/focus events now coalesce into a single animation frame and skip unchanged CSS variables and notifications. No global WebView timer pause, forced cache clear, renderer priority override, upload interruption or release signing change. First verify Android native release compilation and frontend tests; physical-device testing of keyboard, gallery grants/revocation, notifications, call continuity, upload progress, memory and cold/warm startup remains required. No measured performance claim or APK publication.

## Reels media efficiency

The feed now mounts only the active video when device-local lowerData or the browser's available Save-Data signal is enabled; the normal active/adjacent window stays unchanged. Hidden pages remove the mounted feed videos and stop automatic page prefetch; lower-data pagination starts at the last loaded item. Distant thumbnails use lazy loading and only the active card has the ambient blur/spinner. HLS fallback no longer explicitly reloads on every pause or swipe. Detail viewers without a thumbnail use a solid background instead of a second autoplaying MP4; hidden detail playback pauses and can be manually resumed. Preserve native HLS/MP4 source selection, original source quality, object-contain and audio behavior. Browser preload is a hint, not a byte guarantee. No forced quality downgrade; no actual data savings or first-frame measurement claimed. Verify cold and warm scrolling, return from background, explicit autoplay preferences, source replacement, native HLS/fallback, and real bytes/stalls on Android before release. This does not yet resolve all existing watch-time accounting or autoplay-preference inconsistencies.

## Comparable benchmark records (offline)

Use `node backend/scripts/evaluate-performance.mjs baseline.json candidate.json`. No requests are made. Record schemaVersion=1, app, version, sessionId, metric, scope (staging or ordinary_client), device (model/RAM), os (including WebView version where relevant), networkProfile, region, cacheState (cold/warm/not_applicable), workload (content sizes and interaction), protocol (test procedure version), measurementMethod and samples. Each sample is { "ok": true, "ms": 123 } or { "ok": false, "ms": null }. Use distinct sessions, identical conditions, 30–1000 attempts per run, equal sample counts; record failures and do not drop slow observations. Use the literal networkProfile "good" only for a documented good-network protocol; constrained networks do not inherit the good-network budgets. Record exact connection characteristics in the protocol/workload documentation, raw trace locally and a randomized/interleaved repeated-run procedure to mitigate variance. Cached API, feed API, chat delivery, Reel first rendered frame and initial usable content are distinct metrics (cached_api, feed_api, chat_delivery, reel_first_frame, app_usable). Competitor comparison is only ordinary-client chat, Reel first frame or usable-content timing, not private API probing. The evaluator reports nearest-rank successful p50/p95/p99 and failure rate, rejects mismatched conditions and withholds latency change when any attempt failed. Outputs are descriptive; no statistical confidence or blanket speed superiority. The CI fixtures are synthetic only, not real competitor timings. Collect staging and physical-device samples separately before declaring the phase complete.

Example collection protocol: on the same representative Android device, use the same documented Wi-Fi/mobile profile (RTT, download/upload rate, packet loss), similar fixed-duration/resolution content, no unrelated background traffic, same app and OS/WebView versions per run, independent sessions, alternating app order. Cold app usable = launch to visible actionable initial content; warm app usable = resume to usable screen; Reel first frame = swipe/tap to first rendered video frame (not poster); chat delivery = sender action to visible recipient message on paired controlled accounts with a common monotonic observation method. Measure failures/timeouts and rebuffering, bytes and battery separately. No synthetic sleeps presented as actual product performance; no production load tests or competitor automated traffic.
