# Backup and disaster recovery readiness

The disposable CI exercise uses the active Prisma schema in a fresh PostgreSQL 16 source container. It populates synthetic identity, wallet, ledger, post, conversation, participant, message, notification and upload rows. Source is quiescent, logical pg_dump custom-format archive and a synthetic media tarball are checksummed, and a deliberately damaged copy is detected. Source is stopped; pg_restore applies the archive in one transaction to a different fresh database with no external networking. The restored selected row snapshots must match exactly; constraint probes verify unique usernames and author foreign keys; wallet and message relationships and media metadata/bytes must match. Temporary archives and containers are removed. Logs report synthetic backup age and restore/validation time, not a measured production RPO or RTO. No live credentials, persistent user data or provider resources are used.

This uses prisma db push only for disposable CI, not migration replay. It does not cover all business tables, queue migration-only schema, concurrent write snapshots, database roles/ACLs, secrets, WAL/PITR, Cloudinary object backup, real service traffic or production-grade encryption/retention. The disposable recovery exercise passed GitHub CI run 45592987552 on commit faad4b9. No real user-data backup has been created or restored.

Managed staging acceptance: independently verify source and isolated target identity, backups and access; quiesce writers or use a documented consistent snapshot and matching media version; verify encrypted backup checksum and retention; restore only to fresh staging resources with restricted egress and new secrets; validate migration history, schema, row counts, ledger invariants, session invalidation, uploads including private authorization, media bytes, queue leases and representative workflows. Record backup timestamp, cutover/recovery timestamp, lost writes if any, observed RPO and RTO, costs, rollback and owner. Do not restore over an existing database. Production recovery and retention policies require explicit separate approval.


## R2 acceptance drill (PR #282)
`backend/scripts/acceptance-r2-recovery.mjs` requires the isolated acceptance worker identity, exact expected commit, dedicated database host, explicit opt-in `VANTA_R2_RECOVERY_ACCEPTANCE=yes`, and bucket-scoped R2 credentials. It creates two empty scratch databases on the isolated PostgreSQL 18 cluster, adds only synthetic fixtures, dumps the source and archives synthetic media, encrypts each artifact using a fresh ephemeral AES-256-GCM key, verifies ciphertext and restored content, restores to the second database, checks foreign keys, and removes only its own objects and scratch databases. Existing application rows are not copied. Test archives are capped at 8 MiB; the temporary SDK install is pinned and receives no credentials. The envelope unit tests run in CI. This is a bounded acceptance harness, not a scheduled production backup, and has no durable key escrow, cross-cluster restore, full application schema backup, streaming large-object handling, production media access, or retention automation. Never run it against production. An interrupted run can leave synthetic artifacts requiring reviewed cleanup. Before production activation select a supported streaming backup tool, dependency lock and independently held recovery key, restrict credentials, validate consistent database/media recovery points and independently restore verified copies. No backup retention or cost guarantee is established by the drill.


## Public-key backup encryption candidate
Use native age X25519 recipient keys: generate the real identity offline on an owner-controlled trusted device with `age-keygen -o vanta-recovery-key.txt`, obtain the public recipient with `age-keygen -y vanta-recovery-key.txt`, and keep two independent secure copies of the private identity. Never place the private key in Railway, GitHub, R2, logs, or chat. Only the public recipient (`VANTA_BACKUP_AGE_RECIPIENT`) belongs on an approved backup writer. Keep retired identities until every associated backup has expired and independently verify the new recipient before rotation. Losing all private copies makes encrypted backups unrecoverable.

`backup-age-encrypt.sh` accepts stdin, uses age authenticated streaming encryption, writes only encrypted output to a private mode-0700 scratch directory, and atomically publishes a new local .age file without clobbering an existing one. The caller MUST check producer pipeline exit status with pipefail; a valid encrypted prefix is not a successful database or tar backup. Do not upload failed pipelines. The 32 MiB disposable CI test covers byte-exact recovery, wrong key, corruption, truncation, no-clobber, invalid recipient and producer failure. Recovery requires verification of the complete decrypted stream before using it; never stream unverified plaintext directly into a database restore. The staging recovery image adds age and rclone for future isolated tests. This is not production automation: no R2 multipart upload implementation, no disk-capacity budget, no retention, no consistency fence, no manifest publication, no owner key validation and no production deployment yet. The writer can still delete ciphertext with current Object Read & Write credentials; separate immutable retention controls and independently restricted recovery access remain necessary.


## Bounded SDK multipart writer candidate
`backup-r2-multipart.mjs` extracts the verified SDK transfer pattern into a reusable acceptance-only module. It requires an injected S3 SDK/client, fixed private bucket and UUID acceptance prefix, a private regular age ciphertext file, explicit size budget (hard maximum 10 GiB, not a tested capacity), sequential 5 MiB parts, conditional completion and full remote streaming SHA-256 verification. It aborts only its own known multipart upload on failure and reports uncertain completion for reconciliation rather than deleting objects. It never uploads a plaintext manifest or declares a backup set verified before both ciphertext artifacts are verified. The local manifest candidate does not prove producer consistency, private-key recovery or successful restore. Mock CI tests cover parts, remote corruption, ambiguous completion, abort and unsafe targets. The age header is a format sanity check, not cryptographic proof; caller must invoke the tested age producer and verify pipeline success. No production paths, schedules, automatic deletion, dependency lock or live invocation are enabled by this module. Production use requires a separately approved orchestration layer, disk and network budgets, pinned SDK dependency closure, writer fencing, encrypted authenticated manifest, retention and independent restore. The previous live SDK probe succeeded for 32 MiB; this extracted module still needs its own live test. Prior rclone synthetic object removal remains unconfirmed.

## Encrypted manifest publication candidate
The acceptance-only multipart module now permits the exact `manifest.json.age` marker and exposes a publish-last helper. It requires two verified data artifacts, constructs a bounded manifest in memory, invokes an injected trusted age encryption function and verified uploader, and only returns transfer success after the marker itself is remotely verified. A parser checks the decrypted manifest's exact artifact names, sizes, checksums and expected run ID. The marker is not a signed proof of origin or evidence of a consistent source snapshot, and public-key encryption alone does not authenticate the sender. Production needs independently trusted manifest provenance, source fencing, and full independent restoration. Mock tests exercise publication order, failed data/marker verification and cross-run or duplicate-object rejection. This helper is not yet wired into a live orchestration or schedule. Owner must generate the permanent recovery identity independently and retain it outside Railway; only the public recipient is configured on a backup writer. Do not use an ephemeral CI key for real backups.


## Integrated age backup set drill
`backend/scripts/acceptance-age-backup-set.mjs` is a separately opt-in isolated worker drill (`VANTA_AGE_BACKUP_SET_ACCEPTANCE=yes`). It creates fresh scratch PostgreSQL 18 databases, streams a synthetic logical dump and 6 MiB media fixture through age with pipeline failure checking, uses the committed multipart writer and publishes the encrypted marker last. Recovery downloads and validates the marker before selecting the two artifacts, verifies ciphertext and decrypts with an ephemeral test identity, restores to the empty scratch database and directory, checks rows, foreign keys and media bytes, then checks removal of its own artifacts and databases. The owner private key is not used. This is bounded synthetic acceptance, not a production scheduler or independent cluster restore. The temporary SDK dependency closure, source fencing, durable signed provenance, disk budgets, credentials, retention and production access remain separate gates.


## Backup operating policy candidate
The pure `backup-run-policy.mjs` guard defaults to a conservative 8,000,000,000-byte **planning** budget for R2, including all existing objects, incomplete multipart bytes and the proposed set, and requires at least 256 MiB scratch reserve in addition to the planned ciphertext artifacts. The 8 GB value is not a hard provider billing cap or a guarantee of free service (account-wide storage, operation and network usage matter). A fresh, complete measured inventory and validated capacity inputs are mandatory. The guard refuses to authorize a run unless explicitly enabled, separately owner-approved, a real exclusive writer lock is held, all relevant writers are fenced for a matching database/media point, the permanent recipient and independent recovery copies are verified, production credentials rotated and dependencies locked, and no prior attempt remains unresolved. Caller-supplied assertions are not proof; the production orchestrator must obtain independent evidence and enforce byte limits while writing. No actual scheduler, lock, fence, disk quota, upload or production access is introduced here.

Suggested starting cadence is daily in a measured low-traffic window, with an overdue threshold of 26 hours for verified transfers and 31 days for an independent restore. Failure or missing evidence is unhealthy; a successful cron launch is not a successful backup. Candidate retention defaults to seven days and preserves at least two independently restored, provenance-verified backup sets even when older; unverified, held, locked or incomplete sets require separate reconciliation. It never deletes objects. No retention rule or alert delivery is enabled until the owner approves a measured budget, recovery targets and retention period.

### Production activation gate
1. Confirm two independently secured copies of the owner identity, and test decryption from a copy without exposing it to a writer.
2. Use separate narrowly scoped production backup credentials, revoke the staging test token before any real backups, and establish independently restricted restore credentials and provider retention controls. Review the earlier exact synthetic rclone prefix, not unrelated objects.
3. Measure production database size and media bytes plus encrypted scratch capacity using read-only tooling in the actual source environments; verify PostgreSQL client/server compatibility. Do not infer actual usage from volume capacity.
4. Obtain a supported, separately approved access path to the backend's existing /data mount. Railway volumes cannot be assumed to be accessible from another service. Preserve existing mount, paths and URLs. No restart, mount swap, or live source read is authorized by this policy.
5. Implement and test a source fence that covers every write path and holds through matching database/media capture; enforce exclusive writer ownership, runtime byte budgets, locked SDK dependencies and trusted manifest provenance. Do not claim a consistency point from pg_dump alone.
6. Run a single approved production capture, then independently restore to isolated infrastructure and reconcile all required database invariants and media originals before scheduling. Record observed size, cost, RPO and RTO. Only then approve recurrence, retention and real alert delivery. No production schedule is currently active.
