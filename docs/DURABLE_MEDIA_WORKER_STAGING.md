# Isolated durable media worker staging

This worker is deliberately separate from the HTTP backend and must not be enabled in production as part of this PR.

## Staging prerequisites

- Deploy the PR branch `infra/phase6-6-to-6-12-readiness` in a **dedicated Railway service**; do not repoint the existing staging HTTP backend.
- Provision a dedicated staging PostgreSQL database with the QueueJob migration applied. Do not reuse the production database.
- Provide a storage architecture where both the HTTP producer and media worker can read the same uploaded bytes. Railway volumes attached to separate services **are not shared**; a worker-only volume at `/data/uploads` is insufficient. Do not move/detach existing volumes as a workaround.
- For the current **local-only** durable media handlers, set `UPLOAD_STORAGE_DIR` to the shared local upload path. The worker now checks up to 25 recent non-Cloudinary backend upload records and refuses to start media processing unless at least one matching real file can be read with the expected byte size. This is a startup smoke test, **not** full proof of durability or all-uploads access.
- VANTA's HTTP uploader already supports Cloudinary. An **opt-in alternative** worker mode is now available with `VANTA_DURABLE_QUEUE_MEDIA_STORAGE=cloudinary`. It uses the existing Cloudinary provider to prepare image/thumbnail variants and managed HLS derivatives, without needing shared Railway volumes. Cloudinary jobs have distinct type names (`cloudinary:image:optimize`, `cloudinary:thumbnail:generate`, `cloudinary:video:transcode`) so they can never be claimed by the local FFmpeg/Sharp worker. Jobs in this mode reference a validated `UploadedFile.id` (`{ "fileId": "..." }`) rather than paths, and can only transform an existing, non-deleted VANTA Cloudinary image or video. Message assets remain `authenticated` rather than public.
- Cloudinary mode excludes all local media types (including `cleanup:temp`) from claims; the default local mode retains the original FFmpeg/Sharp handlers. The new Cloudinary path **has not been validated against real provider credentials**; output URLs are not yet connected to the user-facing upload/playback model. The producer is disabled by default. Do not enable this mode in staging or production until that integration is completed and tested. Large HLS eager transformations can incur provider costs and processing time.
- Storage diagnostics now separate local and Cloudinary file references: remote uploads must **not** be counted as missing local files. `remotePresenceVerified=false` explicitly indicates this is not a Cloudinary availability check; `metadataProbeSucceeded=false` means the database could not be inspected. A missing local upload is still unhealthy, even in Cloudinary mode.
- Cloudinary producer is separately opted in with `VANTA_DURABLE_QUEUE_MEDIA_PRODUCER=true`, which requires Cloudinary storage. When enabled, the HTTP uploader writes its `UploadedFile` row and derived media queue jobs in **one PostgreSQL transaction**. Reels, stories and post videos enqueue managed HLS; images enqueue optimization and optional thumbnails. Keep this flag disabled until the worker/provider/output delivery has been verified.
- The `UploadedFile.optimizedUrl`, `UploadedFile.thumbnailUrl`, and `UploadedFile.hlsUrl` nullable columns preserve verified derivative URLs. Apply their database migration before enabling the worker. A derivative may be written only when the original source path still matches and the asset has not been deleted or marked private.
- Reel finalization now links the uploaded file and marks the Reel as published in one PostgreSQL transaction. If linking fails (deleted, reassigned, or no longer owned), the Reel must not publish. Test this with direct and chunked uploads before enabling HLS delivery.
- `VANTA_DURABLE_QUEUE_MEDIA_DELIVERY=true` exposes an available linked Reel `hlsUrl` in Reel feed/detail API responses. Disabled by default; the original `videoUrl` (MP4) remains unchanged for playback fallback. Browser HLS playback still requires compatibility testing.
- Derivative publication now verifies the exact Cloudinary account, resource type, and original VANTA public ID in each returned URL, as well as HTTPS and the expected extension. Wrong-account/wrong-asset URLs must never be saved as playback sources.
- Cloudinary credentials are an **all-or-none** configuration. Supplying only part of `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET` now fails HTTP backend startup rather than silently selecting local disk. Never print secret values. This change does not migrate existing local assets.
- Provide Node 22, FFmpeg with libx264 and AAC, and the Sharp native module in the worker image. Verify `ffmpeg -encoders` and `node -e "require('sharp')"` during build. CI tests FFmpeg but does not provision a production worker image.
- For **local mode**, ensure `/data/uploads` exists, is not a symlink, and is readable and writable before starting the worker. The entrypoint refuses unsafe or missing local storage. For **Cloudinary mode**, configure all three Cloudinary credentials and keep the Cloudinary media flag disabled until provider acceptance testing. Set `DATABASE_URL` to the isolated staging database and `VANTA_DURABLE_WORKER_ENABLED=true`. Only set `VANTA_DURABLE_QUEUE_MEDIA_HANDLERS=true` after the chosen storage path has been proven end to end.
- Start with `node backend/dist/durable-worker.js` after `npm --prefix backend run build`. Do not start the HTTP server in this service.

## Acceptance checks

1. Upload a fresh representative image and video through the **staging HTTP backend**, then verify the worker reads those exact backend-produced bytes; a worker-local fixture alone is insufficient. Enqueue an image and thumbnail job referencing the shared upload. Verify real nonempty WebP files.
2. Enqueue a video transcode and verify master playlist, variant playlists and actual TS segments.
3. Retry each completed job and verify original files and completed outputs remain unchanged.
4. Interrupt a worker mid-job; verify lease recovery and that a stale worker cannot complete the job after its lease expires.
5. Enqueue invalid traversal and unsupported job types; verify no external file reads and terminal failure for unsupported types.
6. Check queue health and job errors, then stop the worker and confirm the HTTP backend remains healthy.

## Release gate

Do not merge based only on green GitHub CI. The staging backend currently uses a different branch from this worker and has no mounted upload volume; the worker's private `/data/uploads` volume cannot access its files. Media handlers must remain disabled until the producer/worker storage boundary has been solved and tested. Cloudinary remote processing avoids the local volume boundary, but still needs provider-level validation, derivative URL integration, private playback checks, and acceptance evidence.  Record staging service ID, deployed commit, FFmpeg and Sharp versions, shared-storage evidence, job IDs, failure/retry results, and rollback procedure. If no shared persistent upload storage exists, media jobs cannot be marked staging-verified.
